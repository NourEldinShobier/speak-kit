# Testing SpeakKit

## Run it

From `code/`:

| Command | What it does |
|---|---|
| `pnpm exec vp test run` | Unit and integration tests of every package (vitest through Vite+). `e2e/` is excluded by `code/vite.config.ts`. |
| `pnpm run typecheck` | `node scripts/typecheck.mjs`: tsrs on every project (what CI runs). One project: `pnpm exec tsrs --noEmit -p <dir>`. |
| `pnpm run lint` / `pnpm run knip` | Lint (oxlint through Vite+; also enforces the module boundaries: the desktop renderer never imports `main/`, extension `app/` imports other features only through their `index.ts`) and unused files, exports and dependencies (knip, `code/knip.json`). Both run in CI. |
| `pnpm run fmt` / `pnpm run fmt:check` | Formatter (oxfmt through `vp fmt`, configured under `fmt` in `code/vite.config.ts`: 200 columns, the existing hand-written style; fixtures and the generated `icon-data.ts` and `tokens.ts` are ignored). `fmt:check` runs in CI. Line endings are LF everywhere (`.gitattributes`: `* text=auto eol=lf`; `.cmd` and `.bat` stay CRLF). |
| `pnpm exec tsrs --noEmit -p <dir>` | Type check (`packages/*`, `apps/extension`, `apps/desktop`, `e2e/tsconfig.check.json`). |
| `pnpm run e2e` | Builds the extension with test hooks into `apps/extension/dist-e2e` (`SPEAKKIT_TEST=1`, own folder so a normal `dist` build cannot overwrite it), runs the fast Playwright suite, then the performance budgets alone (1 worker). |
| `pnpm run e2e:full` | Same plus the `@slow` tests: real Kokoro model through the real server CLI, and the Electron desktop app. Also builds the desktop app. |
| `node apps/desktop/scripts/smoke-installer.mjs` | Silent-installs `release/SpeakKit-Setup-<version>.exe` into a temp folder with an isolated user-data folder and port, runs `smoke-packaged.mjs` on the installed exe (health, voices, one sentence, bundled extension and worker, a second launch that must exit without adding processes, `--quit`, port freed), runs the uninstaller silently and checks the folder is gone. `smoke-packaged.mjs --exe <portable exe>` does the same for the portable build (set `SMOKE_WAIT_S=120`: the first start unpacks 170 MB). |
| `node e2e/run.mjs tests/popup.spec.ts -g "offline"` | Any Playwright args after the script; skips the perf phase. `--no-build` reuses `dist-e2e`. |
| `E2E_HEADED=1` | Show the browser. Default is Chromium's new headless mode (`channel: "chromium"`, supports extensions). |

Perf numbers from the last run are in `code/e2e/perf-results.jsonl` (one JSON object per line) and summarised in `docs/perf.md`.

## How the suite works

- Each test gets a fresh persistent Chromium profile with the unpacked test build, a fresh in-process `packages/server` (fake engine) on a random port, and a fixture web server (`http://localhost:<port>`, served from `e2e/support/pages.ts`). Only the `@slow` suite uses the real Kokoro engine, started as the standalone CLI with the shared model cache in `code/.cache/models`.
- Pairing always goes through the real options page (type port and token), never by writing storage.
- Sound is proven with the offscreen player's `window.__speakkit` hook (state, `framesReceived`, `scheduledMs`, analyser `rms()`, plus `rate`, `ctxState`, `ctxTime`). Playwright cannot see the offscreen document, so the suite reads it over raw CDP (`--remote-debugging-port=0`, `DevToolsActivePort`).
- Every test fails if any extension context logs a console error or throws (service worker, extension pages, content pages, offscreen document). Tests that provoke connection errors declare which messages are expected.
- The popup is opened as a normal tab (`popup.html?tab=<id>`); test builds honour `?tab=` because a popup opened as a tab would otherwise see itself as the active tab.
- Test-only hooks exist only when built with `SPEAKKIT_TEST=1` (`__TEST__`): open Shadow DOM in the content script, `window.__speakkit` in the offscreen page, `globalThis.__speakkit` in the service worker (`command(name, tabId)`, `menu(id, tabId, selectionText)`, `menus()`), and `?tab=` in popup and side panel.

The root `vite.config.ts` sets `testTimeout: 20_000` (the Vitest default is 5 s). The extension package already runs its browser tests with 20 s, and the root run starts all packages in parallel on a loaded machine, where a Chromium or Electron start or a server-with-engine test can pass 5 s without anything being wrong. The value is a ceiling for hangs, not a performance budget: budgets are asserted inside the tests (`docs/performance-contract.md`). Desktop specs set their own 60 s.

## Known gaps (exact)

- Native UI is not driven: the browser's context menu and global keyboard shortcuts cannot be clicked in Playwright. Tests call the service worker's own `onClicked` and `onCommand` handlers through the test hook, and read the registered menu titles and `chrome.commands.getAll()` shortcuts back. Whether Chrome delivers the real key press is untested. Ctrl+Shift+P and Alt+Shift+P are not assigned by Chrome in this setup, so play/pause moved to Ctrl+Shift+Y.
- Real audio output was not heard. Sound is proven from the analyser (RMS) and the AudioContext clock only; no one has listened to voice quality (uint8 vs q8 included).
- The real toolbar popup and the real side panel are not opened: both run as extension tabs. The `activeTab` grant that a toolbar click gives is therefore not exercised, so the popup's `file://` ("allow file access") state is covered only as a restricted state; for a `file://` or `chrome://` tab the tab URL is hidden from the extension and the popup shows the generic "page unreadable" state.
- On-demand content script injection (a tab opened before the extension was installed) is not tested.
- `chrome://` is covered, and so are `.pdf` addresses (any case, query string) and a `file://` tab without file access (`restricted.spec.ts`). Chrome's own PDF viewer and the Web Store page are not driven: the bundled headless Chromium downloads a PDF instead of opening the viewer, and routing `chromewebstore.google.com` through Playwright closes the page; both stay with the pure URL tests (`popup-view.test.ts`, `background.test.ts`).
- Frames: the content script runs in the top frame only (`all_frames` is off in the manifest), so text inside iframes, same-origin or not, is never read (`pages.spec.ts` pins this). A page whose article lives in an iframe reports "page unreadable". Reading frames would be a manifest change and needs a decision.
- Text selected inside an `<input>` or `<textarea>` is read as a selection (`selectionStart` to `selectionEnd`; `pages.spec.ts`, `extract.test.ts`). Password and non-text inputs and whitespace-only selections fall back to the page read. Field values are never part of a page read. The selection bubble does not appear for a field selection; the context menu and the shortcut read it.
- A speak stream stops before its next sentence once its client has left or it was replaced (`packages/server/tests/speak-abort.test.ts`); the several-tabs race now synthesizes nothing for a losing tab after the winner finished (`resilience.spec.ts`, 10 of 10 runs).
- Chrome's service worker idle stop is reproduced with CDP `ServiceWorker.stopAllWorkers`, not by waiting 30 s.
- Only one browser engine and one OS: headless Chromium (bundled, build 1248) on Windows 11. Branded Chrome ignores `--load-extension`; Perplexity Comet (Chromium 156) honours it in its own profile (see Comet below).
- The 10-minute read is simulated, not played: 600 paragraph jumps in about 20 s with the fake engine, measuring the offscreen document's JS heap after a forced GC. Decoded audio held by the player is now measured (`retainedBytes` hook, 250 jumps, under 8 MB, 0 after stop), but the renderer process's real memory (AudioContext internals, worklet) is not.
- Pitch preservation above 2x is checked on the fake engine's pure tones with a DFT of the analyser output, not on speech; gaplessness is the player's own scheduling lateness (`maxLateMs`), not a recording of the speaker output.
- Real-engine timings (first audio about 1.5 s warm path through the shortcut, 0.5 s after a popup warm, 1.6 s cold) were taken on a shared machine at 25 to 50% CPU and move by 30%. The warm shortcut assertion is best of three and allows the larger of 1.5 s and server-only + 0.9 s. Idle windows of 5 and 15 minutes were not waited for: tests use windows of 1.2 to 4 s and read `idleUnloadAtMs` for the longer ones.
- The deep link is faked in the browser (no OS protocol handler is registered in the test profile). The desktop side is real: a second launch with `speakkit://launch` or `speakkit://pair` focuses the first instance. Registering the protocol with Windows (`setAsDefaultProtocolClient`) is skipped under `SPEAKKIT_USER_DATA`.
- The desktop e2e uses the fake engine; only `full.spec.ts` uses real Kokoro, through the standalone server CLI, not through the Electron app (child-process model host under Electron is not tested). Tray icon pixels, toasts and launch at login are not driven; tray state mapping and the Quit dialog are covered in `apps/desktop/tests/shell.test.ts`.
- "Launch at login" in the desktop app and installers are not tested.
- The desktop `config`, `engines`, `export/service`, `reader/service`, `tray` and `system/keys` modules have unit tests (electron mocked where needed) next to the Electron specs. The extension popup (`PopupScreen`), side panel (`SidePanelApp`, `QueuePanel`), options Sites and Shortcuts sections and the in-page launcher (edge tab and pill, bubble, paragraph button, toast) have component tests under linkedom (`apps/extension/src/testing/dom.tsx`; no layout, focus rings or pointer capture, which stay in `content.test.ts` and Playwright). The `ui` package compares the vanilla builders with the React components in `tests/parity.test.tsx` (markup and classes of button, icon button, toggle, pill, kbd, logo, avatar, menu item, progress bar, tooltip); the slider, segmented control, menu and popover surface twins are not compared. `packages/player` is covered through `Player` and by direct tests of the timeline, queue and sentence splitter.
- Visual fidelity against `designs/next/screens` belongs to the visual harness (`code/e2e/visual`, see visual-fidelity.md): it captures every state in light from the built product, diffs it against the designs and builds `designs/built/review.html`.

What cannot be automated here, and what stands in for it:
- **A real global key press.** `globalShortcut` is replaced by an in-memory registry in test mode (`SPEAKKIT_TEST=1`); the hook presses a registered accelerator. Whether Windows delivers Ctrl+Alt+S, and whether another app already owns it, is checked by hand. A conflict is simulated with the hook `foreignShortcuts`.
- **Reading the selection of another app.** The clipboard sequence (clear, Ctrl+C, wait, restore) is unit tested with a fake clipboard; the `keybd_event` call into another process is not.
- **A real Windows toast.** The toast request (title, body, silent flag, click target) is recorded by the hook; whether Windows shows it, plays the sound or honours Focus Assist is not verified.
- **The native tray menu and tray icon pixels.** Menu items are read through the hook (`trayItems`, `clickTray`); the icon bitmaps are unit tested, not looked at in the taskbar.
- **Real installer behaviour on a clean machine** (SmartScreen, per-user install, uninstall) and **auto-update from GitHub** (needs a published release; the flow is tested with a fake updater). The unsigned installer was installed silently and uninstalled on the development machine only.
- **Chatterbox install and a GPU engine** need Python, a CUDA GPU and about 2.4 GB; the Engines page is tested against the fake engine and a stub server.
- Audio output is proven by the player's start and end events, not by listening.

## Comet (Perplexity browser)

Checked 2026-11-01 on Comet 156.0.8078.132 while the user's own Comet was running: a second `comet.exe` with its own `--user-data-dir` and `--load-extension=<dist>` starts as a separate instance, loads SpeakKit (service worker up, `chrome.commands.getAll()` returns `Ctrl+Shift+S/Y/X`) and leaves the running session alone. No `--disable-features=DisableLoadExtensionCommandLineSwitch` was needed. `releases/open-in-comet.cmd` starts that instance (profile `%LOCALAPPDATA%\SpeakKit\comet-profile`, extension from `code/apps/extension/dist` or the folder passed as argument).

The flag does nothing for a profile that is already open (the new process hands its command line to the running Comet), so the normal profile cannot get the extension from the command line while Comet runs. Into the normal profile, by hand: open `chrome://extensions`, turn on Developer mode, Load unpacked, choose `code/apps/extension/dist` (or the unzipped `releases/v0.1.0` extension folder); it stays installed across restarts. Comet's side panel and its own extensions are unaffected.
